Can the new CRM's API feed our field reports? A feasibility check in Claude Code

A commercial roofing client was moving onto Terial - Roofing CRM, and wanted its daily field reports and sales reports to come out of Terial automatically. Before anyone scoped a build, I used Claude Code to find the client's code repository, check 66 report fields against the documented Terial API, research how Terial handles custom fields, and draft the request for live data access.

My role: Ran the feasibility check in Claude Code with the GitHub CLI, checking each requested field against the client's existing code and the CRM's API.

Outcome: I created an HTML summary for the client and we reviewed it together: what was feasible, the order in which the requests would be implemented, and why the remaining requests couldn't be done.

How the session went

Each step below shows what I typed and what Claude Code did with it. I steered, and Claude Code did the searching, reading and cross-checking.

Find and connect to the client's repository

connect to the company repository for [client]
  • Checked my GitHub sign-in and searched the company's GitHub organization with the GitHub CLI.
  • Found three repositories for the client and asked me which one instead of guessing: a data extractor, a reporting research project and a card-export workflow.
  • Cloned the reporting repository and summarized it: which reports can be built, which columns have no data source, and what's blocking the build.
GitHub CLIClarifying questionRepo summary

Check 66 daily report fields against the API

can you tell me if the following fields are found in Terial API … (66 fields pasted from the field report form)
  • Read the repository's API research report, which was built from live test calls to Terial's API.
  • Matched every field on the daily report form (crew, weather, man-hours, deliveries, roof maps, photos and a 25-item safety and quality checklist) to what the API actually returns.
  • Separated "loosely related" fields from "not found anywhere," and explained why each related field still wasn't a true match.
  • Flagged the limits honestly: the earlier research never looked for daily-report endpoints, and Terial's full API spec wasn't available to an API key.
Document analysisField mappingStated limitations

Research custom fields

does terial allow for custom fields
  • Combined evidence from the repo (a custom fields page exists in Terial's web app, but every API path returned "not found" or a login redirect) with a web search of vendor and directory listings.
  • Answered in one line, "yes in the app, not through the API," and said what that means for the client's reports.
  • Cited its sources, and noted that a directory listing is marketing copy, not documentation.
Web searchCited sources

Draft the access request

i need (read only) access to [client]'s live Terial account
  • Explained that the client's Terial admin has to create the access, and identified the right contact from the project files.
  • Drafted the email asking for a read-only API key and a view-only login, and why each is needed.
  • Built in security: asked the client not to email the API key, and suggested a password manager share instead.
  • Offered to save it as an Outlook draft rather than sending anything on my behalf.
Email draftCredential handling

Apply a data-handling rule, and correct earlier work

do not look at [other client]'s repo
  • Deleted its temporary copy of the other client's repository right away.
  • Saved the rule to its persistent memory, so future sessions won't use that repository for this client.
  • Went back over its earlier answer, found which field mappings had relied on the other repo, and marked those fields "unknown" instead of leaving unsupported answers in place.

What the field check found

The daily field report form has 66 fields. After the correction, the API mapping came out like this:

FieldsResultWhy
LocationRelatedThe job site's city and state are on the property record, if that's what Location means.
Total roofing squares installed to dateRelatedThe project has a square footage field, but it's the job's total size (empty in the test account), not squares installed so far.
Total man hoursRelatedBudgeted hours exist only on service tickets, and are empty in the test account.
Superintendent, ForemanRelatedPeople appear only as the assigned person on a sales opportunity. There's no crew or role assignment on a project.
Beginning and ending date and time, operation notes, commentsUnknownNot covered by the approved research. Needs checking against the live account.
Everything else: weather, crew lists and absences, subcontractors, units completed, man-hours used, deliveries, roof maps, photos and every safety and quality checklist itemNot foundNo daily report, crew, weather, checklist or photo data anywhere in the documented API.

Outcome: the team learned that the daily field report couldn't be automated from Terial's API as documented, before anyone scoped or quoted a build. The next steps were concrete: get read-only access to the client's live account, and ask Terial's engineers whether field reports and custom fields can be opened up to the API.

Why I use Claude Code for this kind of work

  • It reads the real source, not a summary. Answers came from the API research and test-call evidence in the repository, so I could trace every claim.
  • It asks when the choice is mine. With three possible repositories, it confirmed which one before cloning.
  • It says what it doesn't know. Gaps in the research were called out as gaps, not filled in with guesses.
  • It follows data-handling rules and remembers them. One instruction removed the other client's data, fixed the affected answers and became a standing rule.
  • It doesn't act outward without me. The access request stayed a draft for me to review and send.
