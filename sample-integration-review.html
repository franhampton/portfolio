Should a script auto-create CRM leads from email?

A client asked to turn back on a script that reads project managers' Gmail and automatically creates leads in their CRM, which the existing integration then pushes into their field-service system. I reviewed the script's code and the live integration against what the client actually needed, and recommended a built-in feature instead.

The ask vs. what the code did

The goal was simple: every new customer email should end up as a correct lead in Close, with nothing slipping through. Reading the script and the integration showed where the current approach fell short of that.

What the client needed

  • New customers captured from email
  • Existing customers matched to their record, not duplicated
  • Required fields filled in for reporting
  • Vendors and spam kept out of the CRM and field-service system
  • Nothing silently missed

What the script actually did

  • Created the lead before anyone checked who the sender was
  • Pushed every lead straight into SmartGlazier through the webhook
  • Left Source of Lead, Record Type and Customer Type blank
  • Read the thread's last sender, so a PM's own reply could become a lead
  • Labeled threads processed even when the API call failed

Recommendation

Instead of re-activating the Gmail script, have PMs add new senders from Close's built-in Potential Contacts tab. The PM decides "new customer, existing customer or not a customer" with one click, before anything is created. No custom code to maintain, and it uses the current Close setup.

Recommended workflow

  1. A customer emails the PM's Gmail. (No change.)
  2. Close lists the sender under Potential Contacts, already filtering out spam, automated and internal email.
  3. Once a day, the PM works through the Potential Contacts tab.
  4. For each sender: attach an existing customer to their lead, create a new lead with the required fields, or discard a vendor or irrelevant sender.
  5. Close attaches the email, and the sender's earlier emails, to the lead automatically.
  6. The existing webhook creates the SmartGlazier customer, now from a lead the PM has checked. (No change to the integration.)

Why it's the better approach

Both approaches still need one PM decision per new sender. The script just made that decision after a lead and a SmartGlazier customer already existed, so a wrong guess had to be cleaned up in two systems.

Trade-offs, stated plainly: Potential Contacts is a manual click, each PM sees only their own list, and entries expire after 30 days. A daily check of the tab handles all three.

If the team keeps the script

If Potential Contacts doesn't work for the PMs, the script is a reasonable fallback once these code changes are made:

  1. Skip senders on the company's own domain, and read the first outside sender in the thread instead of the last message.
  2. Leave automatic domain matching out.
  3. Set Source of Lead and Record Type at creation, and replace the "Verify and assign" task with a Smart View.
  4. Apply the processed label only after Close confirms the lead was created, so failures are retried.
  5. Store the API key in Script Properties instead of in the code.

Client name, people and email domains are replaced with generic labels. Software names are unchanged.
